# クラス設計・コメントのレビュー（2026-09-04）

対象: `3ee44b874d57`。公開に向けた初回レビュー。

以下は修正前の記録です。後続の不具合修正とBGMパネル分離は
[改修記録](remediation-2026-09-04.md)を参照してください。

結論: `EditorLayer` と `Scene` は責務の集中が強く、神クラス化していると判断する。ファイル単位の分割は進んでいるが、状態の所有者と変更理由の分離が不足している。コメントには意図を説明できているものも多い一方、APIの契約と一致しない説明がある。

## 調査範囲と限界

- `src`、`tools`、`tests` の C++ ファイルを行数で集計し、大きなクラスのヘッダー、実装、呼び出し元を重点的に確認。
- Editor、Scene、Graphics、CLI、Portable の主要な責務と、公開APIコメントの一部を確認。
- 行数には空行・コメント・補助関数も含む。行数だけを問題の根拠にはしていない。
- 下記の初期化漏れは既存 Release DLL にリンクした小さな確認プログラムで再現した。その他はソースレビューによる指摘。
- 全関数・全コメントを精査したものではなく、セキュリティ、ライセンス、全機能の動作監査でもない。今回、既存テスト一式の再実行や本体の変更はしていない。

## 優先度 高: 実際の動作・API契約

### 1. Scene の初期化漏れ

根拠: `src/LamaPon/Scene/Scene.cpp:3809`、`SceneSerialization.cpp:4568`、`:4731`、`:4750`、`:4857`。

`Clear()` は Fog、Bloom などを初期化するが、TAA、SSR、Volumetric Light の設定を初期化していない。通常のシーン読み込みは `Clear()` を呼び、JSONに項目がある場合だけ設定を上書きする。そのため、これらの項目を省略したシーンには直前の設定が残りうる。

確認プログラムで各設定の `enabled` を初期値の反対へ変更して `Clear()` を呼ぶと、次を出力した。

```text
taaReset=false ssrReset=false volumetricReset=false
```

修正案: シーン固有の描画設定・履歴状態をまとめて初期化できる構造にする。まず個別の初期化漏れを修正し、設定済みシーンから項目省略シーンへの読み込みを回帰テストに追加する。タグなど意図して残すプロジェクト設定とは分離する。

### 2. 公開コメントが現行APIと一致しない

根拠: `src/LamaPon/Graphics/RenderPipeline.h:39`、`RenderPipeline.cpp:118`、`src/LamaPon/Scene/EventBus.h:23`、`src/LamaPon/Scripting/Script.h:432`。

- `RunDepthPrepass` は戻り値を true / false と説明しているが、実際は `DepthPrepassResult`。また「SSAO無効なら処理しない」という説明に対し、実装はSSRだけが有効でも深度プリパスを実行する。`ambientOcclusionResolved` と `depthAvailable` を別々に説明する必要がある。
- `EventBus` は「購読はScript破棄時に自動解除」と説明しているが、生の `EventBus::Subscribe()` は数値ハンドルを返すだけで、Scriptへ登録しない。自動解除は `Script::On()` を通した場合などの寿命管理による。生のAPIを直接使う読者が解除を省略すると、破棄済みオブジェクトを捕捉したコールバックを残す危険がある。

修正案: APIコメントに、所有者、解除責任、戻り値、例外、呼び出せるスレッドを必要に応じて記載する。開発時の出来事より、呼び出す側が守る契約を優先する。

## 優先度 高: 次の機能追加前に分離したい責務

### 3. EditorLayer はファイル分割後も一つの巨大クラス

根拠: `src/LamaPon/Editor/EditorLayer.h:61`、`:509`、`:588`、`:663`、`:870`、`:969`、`EditorLayerInspector.cpp:2720`。

- `EditorLayer*.cpp` は8ファイル、合計39,011行。ヘッダーは1,222行。
- ヘッダーに現れる異なる `m_` 名は271個。これはネストした型もあるため厳密なメンバー数ではなく、規模の補助指標。
- Inspector、アセット取り込み、Undo、パッケージ用ワーカー、ビルド監視、外部ツール、道路・車両・BGM編集などの状態と処理を同じクラスが所有する。
- `DrawInspector()` は約10,300行で、各種コンポーネントと環境設定のUIが一つの関数へ集まる。
- パネル種別は `ProjectPanelKind` と分岐に固定されている。道路幅・ホイールベース・曲の試聴などのプロジェクト向け処理を追加するたび、エディター本体へ変更が入る。

影響: 独立したツールの変更が共通状態へ触れやすく、単体での検証や外部開発者による拡張が難しい。CPPを増やすだけではこの問題は解消しない。

修正案: BGMパネルから独立した状態・ロード・保存・試聴の所有クラスを抽出する。Inspectorはコンポーネント単位の描画担当へ分割する。共通Contextは必要な操作に絞り、`EditorLayer&` 全体や全privateメンバーへアクセスする仕組みにはしない。ゲーム固有のステージ／道路／車両編集は、本体の改修計画から除外する。

### 4. Scene がオブジェクト管理・物理・描画・保存を直接担当

根拠: `src/LamaPon/Scene/Scene.h:93`、`:673`、`:741`、`:785`、`Scene.cpp:4584`、`:6288`、`:7733`、`:8282`。

`Scene.cpp` は8,885行。別ファイルの `ScenePhysics.cpp` と `SceneSerialization.cpp` も同じSceneの責務を実装している。GameObjectの所有に加え、衝突解決、可視性、ライト収集、プローブベイク、GI、ポスト処理履歴を直接持つ。前述の初期化漏れは、状態追加時に全体の初期化を追従させる難しさが表れた具体例。

修正案: `SceneRenderer`、`PhysicsWorld`、シリアライズ担当へ順に移す。既存の `Scene` 公開APIを窓口として保ち、内部委譲によりゲーム側の変更を抑える。レンダーターゲットと履歴状態の寿命も描画担当側へまとめる。

## 優先度 中: 依存関係・変更範囲の縮小

### 5. GraphicsDevice が音声・入力の所有者でもある

根拠: `src/LamaPon/Graphics/GraphicsDevice.h:373`、`:624`、`GraphicsDevice.cpp:240`。

D3Dデバイス・描画リソースの管理に加え、AssetManager、AudioSystem、InputSystemも所有し、`Shutdown()` で同時に破棄する。音声・入力を使う処理まで描画デバイスへ依存し、ヘッドレス実行や個別の初期化・終了を扱いにくい。

修正案: アプリケーション側で各サービスの寿命を管理し、必要なサービスだけを渡す。移行中は既存のアクセサーを互換窓口として残し、公開ABIとゲームモジュールの再ビルドに配慮する。

### 6. CLIの入口ファイルへ多数のコマンドが集中

根拠: `tools/LamaPonCli/Main.cpp:5637`、`:7047`、`:7947`、`:8223`、`:8498`。

9,697行に、スキーマ、パッチ、描画、学習、ビルド、書き出し、引数処理などが同居する。これは神クラスではなく巨大な翻訳単位の問題。コマンド単位の変更・レビュー・検証を分離しにくい。

修正案: コマンド群ごとの実装と必要な共通Contextを分け、Mainには引数解析と振り分けを残す。出力JSON・終了コードの互換性を既存CLIテストで確認する。

## 良い点

- フォルダー単位では Audio / Assets / Graphics / Physics / Reactive 等に分かれている。
- `GameModuleBuilder`、`PackageManager`、`SceneManager`、レンダーパイプライン関数など、分離済みの実装を次の抽出先として使える。
- RAII、明示的な所有権、例外境界、キャッシュやDLLをまたぐ状態の意図を説明するコメントがある。コメントの量を増やすより、既存説明の正確さを揃える方が効果的。
- シーン保存、物理、描画、Game Module、リアクティブ処理などの回帰テストがあり、段階的な改修の土台になる。

## 改修順序

1. 初期化漏れと誤ったAPIコメントを小さい変更で修正。
2. BGM、Inspectorの共通機能から状態と操作を移す。独立描画・保存・再読み込み・試聴終了を確認。ゲーム固有の編集機能は対象外。
3. Sceneの描画状態・ベイク処理を抽出し、その後に物理・保存の境界を整理。エンジンの描画・物理・保存・Game Module回帰テストで確認。
4. GraphicsDeviceのサービス所有とCLIのコマンド分割を個別に進める。

`CONTRIBUTING.md` の「パネルを別の翻訳単位へ分ける」という規約には、独立した責務には独立した状態所有者と限定した依存を設ける基準も加えたい。任意の行数上限だけで設計の良否は判断しない。
