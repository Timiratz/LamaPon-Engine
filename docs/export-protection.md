# 書き出したゲームの保護

エディターの「プロジェクト設定とビルド...」→「ビルドプロファイル」でWindowsを選んだときの配布物について、
どこまで守られていて、どこからは守れないのかをまとめます。ここで説明する実行ファイル、
DLL、`assets.tpak`の保護はWindows出力が対象です。**エンジン本体（このリポジトリ）は公開する前提**なので、
「実装が秘密であること」に依存した仕組みは使っていません。

## 配布物に入るもの

```
MyGame.exe              ゲーム本体（LamaPonGame.exeをコピーして改名。gameIcon指定時はアイコンも置換）
LamaPonRuntime.dll      エンジン。この配布物専用の鍵が焼き込まれています
LamaPonGameModule.dll   あなたのC++スクリプト
assets.tpak             アセット一式（暗号化）
shader-cache/           事前コンパイル済みシェーダー（暗号化）
LamaPonGame.json        起動時の設定（平文）
```

`assets`フォルダーは配布物へ入りません。シーン、テクスチャ、モデル、
マテリアル、音声はすべて`assets.tpak`の中です。

Windows書き出しでは、`assets/`内にあるC/C++ソースとヘッダー、
デバッグ情報（PDBなど）、ビルド成果物、実行可能ファイルを
`assets.tpak`から除外します。ゲーム用C++は`LamaPonGameModule.dll`へ
コンパイルされます。独自拡張子の実行時アセットは、拡張子の登録なしで
引き続き梱包できます。

梱包した相対パス、除外した開発用ファイル、アーカイブ外の配布ファイルは、
書き出し時のエディターログに一覧表示します。この一覧を平文ファイルとして
配布物には入れません。アーカイブ外にもソースや認証情報らしいファイルが
混ざっていないか、公開前に確認します。
`.env`、秘密鍵、資格情報ファイルと思われる名前や、`assets/`内の
シンボリックリンクがある場合は書き出しを止めます。名前による検査であり、
任意のJSONや画像へ埋め込んだ秘密を自動検出するものではありません。

## やっていること

### 1. アセットは1本のアーカイブへ暗号化して入る

`assets.tpak`はAES-256-CBCです。ファイルごとに別のIVで暗号化するので、
1つのアセットを読むために全体を復号する必要はありません。
**ファイル名の索引も暗号化**されているので、アーカイブを開かずに
「何が入っているか」を見ることもできません。

読み込み時は、ファイル長を確かめてから索引を確保します。索引は暗号文で
64 MiB以下、エントリは最大10万件、相対パスはUTF-8で4096バイト以下、
各アセットの暗号文は512 MiB以下です。各エントリの範囲、連続性、
重複パス、不正なパスや余分なデータも検査して拒否します。
書き出し側も同じ上限を使い、超えるアセットはエラーにします。
大きなアセットは分割してから書き出してください。

### 2. 鍵は書き出しごとに新しく作る

**エンジン共通の鍵は使いません。** 書き出しのたびに乱数で鍵を作り、
その配布物の`LamaPonRuntime.dll`へ直接焼き込みます（DLLのバイト列を
書き換えるので、エンジンの再ビルドは要りません）。

これで「1つの配布物から鍵を抜いた人が、別の配布物も開ける」
状態を防ぎます。エンジンを公開するとソースを読むだけで共通鍵が手に
入ってしまうので、ここは共通にできません。

焼き込む場所には目印の並びがありますが、**書き込みと同時に目印は乱数で
潰します**。配布物のバイナリを検索しても「ここに鍵がある」と分かる並びは
残りません。

### 3. 改ざんを検知する

アーカイブの各エントリと索引には、暗号文に対するHMAC-SHA256が付いて
います。復号する**前**に検証し、合わなければ例外にして止めます。
アセットを差し替えた配布物は、黙って動くのではなく起動に失敗します。

HMACのない形式は現行ランタイムで開けません。その形式で書き出したゲームは、
**現行ランタイム向けに再エクスポートしてください。** 読み取りを許可すると、
改ざんする側がHMACのない形式へ戻すことで検証を回避できるためです。

### 4. シェーダーはソースを外し、バイトコードも暗号化する

プロジェクト設定の「書き出しでHLSLソースを外す」（新しいプロジェクト
では既定でオン）を入れると、`.hlsl`と`.hlsli`は配布物へ入りません。
同梱するのは事前コンパイル済みのバイトコードだけで、**そのバイトコードも
同じ鍵で暗号化**します。素のDXBCを置くと逆アセンブルで中身を読めて
しまうためです。

### 5. 解く側の手掛かりを配らない

エンジンの配布ZIPには、暗号化まわりのヘッダ
（`Crypto.h`／`AssetPacker.h`／`AssetArchive.h`）を入れていません。
Game Moduleのビルドには要らないヘッダです。

ただし**これは目印を減らすだけで、暗号上の防御ではありません**。復号する実装は
どの配布物にも`LamaPonRuntime.dll`として同梱されるため、形式は
配布物そのものから解析できます。書き出しごとに鍵を変える目的は、1つの配布物から
取り出した鍵を別の配布物へ流用できないようにすることです。各配布物を個別に解析される
可能性は残ります。

### 6. デバッグ情報は配らない

配布ZIPにもゲームの配布物にもPDBは入りません（クラッシュ解析用のPDBは
別のsymbols ZIPで配布します）。

### 7. Windows配布物へコード署名する（任意）

Windows SDKの`signtool.exe`と、自分のコード署名証明書を用意した場合、
エディターのWindows書き出しで「自分のコード署名証明書でEXE/DLLに署名」を
有効にできます。SignToolの絶対パス、現在のユーザーの`My`証明書ストアにある
証明書のSHA-1拇印（40桁）、HTTPSのRFC 3161タイムスタンプURLを入力します。
秘密鍵やパスワードはエディターへ渡さず、署名設定もプロジェクト設定と
配布物には保存しません。証明書はWindowsの証明書ストアで管理してください。

署名対象はゲームEXE、書き出しごとの鍵を埋め込んだ`LamaPonRuntime.dll`、
存在する場合の`LamaPonGameModule.dll`です。音声・VC++ランタイム・
パッケージなどの外部DLLは制作者の証明書で再署名しません。
すべてのファイル変更を終えてからSHA-256で署名し、RFC 3161タイムスタンプを付け、
`signtool verify /pa /all /tw`で検証します。失敗すれば書き出しを中断し、
既存の配布先を置き換えません。配布用ZIPを選んだ場合も、署名済みファイルを
ZIPに入れます。

CLIでも同じ設定を渡せます。

```powershell
LamaPonCli.exe export --project C:\path\to\game --out C:\path\to\release `
  --signtool "C:\Program Files (x86)\Windows Kits\10\bin\<version>\x64\signtool.exe" `
  --sign-cert-sha1 <40桁の証明書拇印> `
  --timestamp-url https://<RFC3161サーバーのURL>
```

配布後のファイルは、Windows SDKの`signtool verify /pa /all /tw MyGame.exe`で
再検証できます。[MicrosoftのSignTool資料](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)
も参照してください。署名は配布元と署名後の改変を検証するためのもので、
リソースやコードの逆解析を防ぐものではありません。署名しない通常の書き出しも
引き続き利用できます。

### 8. Game Moduleの公開情報を点検する

Release版Game Moduleは関数単位で未使用コードを除去し、同じ実装を統合して、
リンク時にも最適化します。別配布のPDBには従来どおりクラッシュ解析に必要な
情報を残し、LamaPonがビルドするRelease版EXE・DLL内のPDB参照は
ファイル名だけにします。
[Microsoftの`/PDBALTPATH`資料](https://learn.microsoft.com/en-us/cpp/build/reference/pdbaltpath-use-alternate-pdb-path)
のとおり、これはPDBの保存先を変えず、DLLに記録するパスだけを変えます。
任意のGame Moduleは次の読み取り専用ツールで点検できます。

```powershell
py -3 tools/audit_game_module.py path\to\LamaPonGameModule.dll --strict
```

`--strict`はビルドPCの絶対PDBパス、または
`LamaPonGetGameModule`以外の公開関数があると失敗します。
ASCIIで8文字以上の連続した文字列とRTTI型名も数えますが、
**文字列の個数は逆解析の難しさを表す指標ではありません。**

同じサンプルGame Moduleを同じRelease環境でビルドして比較した結果です。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| DLL容量 | 534,528 B | 223,744 B |
| ASCIIで8文字以上の連続した文字列 | 1,016 | 710 |
| 絶対PDBパス | 1 | 0 |
| 公開関数 | 1 | 1 |

Game Moduleのロード・Scene更新まで含むテストは変更前後とも成功しました。
同じサンプルゲームの`--validate-startup --warp`を繰り返し、
最後の8回の中央値は変更前618 ms、変更後553 msでした。GPU初期化と
OSキャッシュによるばらつきが大きいため、速度改善の保証値ではありません。
変更後もRelease用PDB（約15.9 MiB）はビルド先に残り、別途クラッシュ解析に使えます。
同じ既存`assets.tpak`からのテストアセット読み取りも両方で成功し、
ウォーム実行はどちらも約40 msでした。Game Moduleの最適化は
アセットの復号経路を変えません。

登録名、エラーメッセージ、必要なRTTI型名はDLLへ残ります。
公開実装である`LamaPonRuntime.dll`にも多数の公開関数名と診断文字列が
残ります。サンプルReleaseビルドでは公開関数が35,162個あり、
モジュールの動作を調べる手掛かりになります。
配布バイナリを解析する人がゲームロジックを理解するまでの時間は、
個別のゲームと解析者に左右されるため、上の数値から推定しません。
追加の難読化は互換性・デバッグ・実行速度への影響を、対象ゲームで
測れる場合に限って検討してください。

## やっていないこと・守れないこと

**鍵は配布物の中にあります。** 復号するのは配布物自身なので、鍵を同梱
しないという選択肢がありません。デバッガーを当てて`LamaPonRuntime.dll`の
`ArchiveKey()`が返す値を読めば、その配布物の鍵は取り出せます。
この仕組みで抑えられるのは次の2点です。

- 1つの配布物から取り出した鍵を、別の配布物へそのまま流用すること
- 目印の単純なバイト検索だけで鍵の位置を特定すること

**次のものは現時点で実装していません。** 導入する場合は、実行時負荷、互換性、
保守コストを機能ごとに評価する必要があります。

- 実行ファイルの難読化・パッカー（VMProtect等）
- アンチデバッグ、アンチチート
- 実行時にゲーム自身が署名を検証する仕組み
- ライセンス認証

**ゲームロジック（`LamaPonGameModule.dll`）はネイティブコードです。**
C#のように元のコードがそのまま復元されることはありませんが、
逆アセンブラーで解析はできます。

**`LamaPonGame.json`は平文です。** 解像度やウィンドウ設定など、
プレイヤーが変えても構わない値だけを置いています。秘密にしたい値を
ここへ入れないでください。

## 秘密にしたい値の置き場所

APIキーやサーバーの認証情報を配布物へ入れないでください。上記のとおり、
配布物の中にあるものは最終的に読めます。サーバーが要る仕組みは、
**サーバー側で認証する**設計にしてください。

Discordログインを使う場合も、Discordの`client_secret`やDiscord access tokenを
`project.json`、`LamaPonGame.json`、Game Module、アセットへ入れてはいけません。
ゲームには公開してよいバックエンドURLとゲーム／環境IDだけを置き、OAuthの秘密と
セーブ所有権の判定はバックエンドで扱います。詳しくは
[Discordログインとクラウドセーブ](online-services.md)を参照してください。
